# Offline test failure audit

Every failing file needs either a test repair, current fixtures, an explicit client feature requirement, or a client fix. The 21 failing files are not evidence of 21 independent client bugs. The message-confirmation suite does expose a current null-receipt bug; several other suites depend on features that have not merged.

Audited on 2026-10-15 with Node v20.19.6, test sources at `b424be0`, and client checkout `92921ba4b51b3792295f5fbb4ea689fc5655de74`. Its application source matches client `bc439f28ada1119a55397fd06d780641db1fefc5`. All 21 files were rerun with `local-tests/run.mjs`. This audit changes documentation only; the failures remain visible.

These counts exclude the 3 opt-in browser scripts and 8 manual HTML fixtures.

## Current client bug

[`queryNetwork`](https://github.com/Liberdus/web-client-v2/blob/bc439f28ada1119a55397fd06d780641db1fefc5/app.js#L11443) can return null when offline or after a transport/parse error. [`checkPendingTransactionsOnce`](https://github.com/Liberdus/web-client-v2/blob/bc439f28ada1119a55397fd06d780641db1fefc5/app.js#L36888) awaits it and then accesses `res.transaction` without a null guard; the same condition calls `Object.keys` on an undefined transaction. These paths are reproduced by the migrated suite. The existing [message-confirmation PR #1802](https://github.com/Liberdus/web-client-v2/pull/1802) addresses null handling together with the bounded observation window. This application issue should remain tracked while test-maintenance work proceeds.

## Repair order

1. Prioritize the current null-receipt bug through the existing message-confirmation PR. Validate that fix against its branch and after integration.
2. Update incomplete harnesses and current API contracts, keeping the underlying behavior assertions. Start with DAO loading/navigation, summary fetching, and the fee mock because temporary corrections already isolate their causes.
3. Replace historical DAO fixtures with synthetic current server-model fixtures. Recovered files are available on `issue-1639-project-proposal-info`, but copying them alone leaves three failures in each affected suite and an inapplicable patch.
4. Give feature/prototype suites explicit client requirements and separate commands or groups. Preserve their assertions and history; avoid blanket skips and misleading green results. The cache-specific expectations in the backend-fetcher suite also need an explicit scope decision. Review the status of closed feature PRs before assuming their implementation should be restored to the current client.

The remaining failures did not establish additional current-client bugs in this audit. This does not prove those features have no bugs; many of the original failing cases stop before exercising their intended behavior.
